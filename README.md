# АгроМаркет API

Backend интернет-магазина «АгроМаркет». В лабораторной №5 API работал с локальными данными; в лабораторной №6 каталог и заявки переведены на PostgreSQL. Ниже сохранены материалы предыдущей лабораторной и добавлена актуальная документация проекта.

## Быстрый запуск проекта

```bash
cd agromarket-server
npm install
npm run dev
```

React-приложение запускается отдельно из каталога `agromarket-react` командой `npm run dev`.

## Лабораторная работа №6 — PostgreSQL и CRUD API

### Цель и архитектура

Перевести хранение товаров и заявок из локальных структур в реляционную БД, реализовать SQL CRUD и связать каталог и форму React с API.

```text
React + Vite (localhost:5173)
          │ HTTP / JSON
          ▼
Express 5 API (localhost:3000)
          │ параметризованные SQL-запросы через pg
          ▼
PostgreSQL 18 (Ubuntu VMware)
```

В этой учебной конфигурации PostgreSQL запущен в Ubuntu VMware по адресу `<VM_HOST>:5432`; база называется `agromarket`, пользователь — `<DB_USER>`. Этот IP относится только к локальной виртуальной машине данного проекта. В другой сети, на другом компьютере или при использовании облачной БД значение `DATABASE_URL` необходимо настроить самостоятельно.

### Настройка и запуск

1. Запустить PostgreSQL в Ubuntu VMware и проверить, что кластер активен (например, `sudo systemctl start postgresql` и `pg_lsclusters`).
2. В каталоге `agromarket-server` создать `.env` на основе `.env.example`, затем указать актуальную строку подключения. Настоящий пароль хранить только в `.env`, не в README и не в Git.

   Пример формата (замените `<PASSWORD>` своим паролем локально):

   ```dotenv
   PORT=3000
   DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DATABASE
   CORS_ORIGIN=http://localhost:5173
   ```

   `.env` исключён из Git; `.env.example` содержит только пример настроек, без пароля.

3. Установить зависимости и запустить Express из `agromarket-server`:

   ```bash
   cd agromarket-server
   npm install
   npm run dev
   ```

   Альтернативная команда запуска: `npm start`. API доступен по адресу [http://localhost:3000](http://localhost:3000).

4. Запустить React в отдельном терминале:

   ```bash
   cd agromarket-react
   npm install
   npm run dev
   ```

   Vite обычно открывает frontend по адресу [http://localhost:5173](http://localhost:5173).

#### Первоначальная инициализация БД

Для пустой БД текущий `package.json` предоставляет команду:

```bash
npm run db:init
```

В методичке эта операция упоминается как `npm run db`, но в текущем проекте такой script **не определён**; фактическое имя — `db:init`. Команда запускает `db/seed.js`, создаёт таблицы и загружает исходные товары. Это только первоначальная инициализация пустой базы. Скрипт намеренно прекращает работу, если таблицы уже существуют; не запускайте его повторно на рабочей БД и не используйте как обычную команду старта сервера.

### Таблицы и ограничения

Схема находится в [`db/schema.sql`](./db/schema.sql).

| Таблица | Основные поля и ограничения |
| --- | --- |
| `products` | `id SERIAL PRIMARY KEY`, обязательные `name` и целочисленный `price`, `CHECK (price >= 0)`, `unit` со значением по умолчанию, необязательные `category` и `image`. |
| `orders` | `id SERIAL PRIMARY KEY`, необязательный `product_id` с внешним ключом на `products(id)` и `ON DELETE SET NULL`, обязательные `name`, `email`, `quantity`, `CHECK (quantity >= 10)`, необязательные телефон, дата доставки и комментарий, статус из `new`, `processing`, `done`, `cancelled`. |

Заявки сохраняют ссылку на товар, а `GET /api/orders` получает название через `LEFT JOIN`; заявки без связанного товара также остаются в выдаче.

### SQL и безопасность

В [`db/lab6-queries.sql`](./db/lab6-queries.sql) собраны примеры и упражнения:

- `SELECT` — чтение всех товаров и выбор отдельных полей;
- `WHERE` — фильтрация, в том числе вместе с условием цены;
- `ORDER BY` — сортировка результатов;
- `ILIKE` — поиск подстроки без учёта регистра;
- `GROUP BY`, `COUNT`, `AVG` — группировка и агрегаты;
- `INSERT`, `UPDATE`, `DELETE` — изменение данных с `RETURNING`.

В API значения пользователя передаются параметрами `pg` (`$1`, `$2` и т. д.), а не вставляются в SQL как текст. Для сортировки используется белый список колонок. SQL-файл содержит упражнения с транзакциями и `ROLLBACK`; их наличие не означает, что они были повторно запущены в ходе этой финальной проверки.

### API-маршруты

Успешные ответы со списками сохраняют массив JSON. Ошибки возвращаются объектом `{ "error": "..." }`.

| Метод | Путь | Назначение | Ответы |
| --- | --- | --- | --- |
| `GET` | `/` | Проверка доступности сервера | 200 |
| `GET` | `/api/health` | Проверка API и соединения с PostgreSQL | 200 |
| `GET` | `/api/about` | Информация о проекте | 200 |
| `GET` | `/api/products` | Список товаров с поиском, фильтром, сортировкой и пагинацией | 200, 400 |
| `GET` | `/api/products/:id` | Получить товар | 200, 400, 404 |
| `POST` | `/api/products` | Создать товар | 201, 400 |
| `PUT` | `/api/products/:id` | Полностью обновить товар | 200, 400, 404 |
| `DELETE` | `/api/products/:id` | Удалить товар | 204, 400, 404 |
| `GET` | `/api/orders` | Список заявок с `product_name` | 200, 400 |
| `POST` | `/api/orders` | Создать заявку | 201, 400 |
| `PATCH` | `/api/orders/:id` | Изменить статус заявки | 200, 400, 404 |

Примеры безопасных GET-запросов:

```text
GET http://localhost:3000/api/health
GET http://localhost:3000/api/products
GET http://localhost:3000/api/products?search=мол&maxPrice=1000&sort=-price&limit=2&offset=0
GET http://localhost:3000/api/products?sort=name
GET http://localhost:3000/api/orders
GET http://localhost:3000/api/orders?status=new
```

Допустимые параметры `GET /api/products`:

| Параметр | Поведение |
| --- | --- |
| `search` | Поиск названия без учёта регистра; специальные символы поиска обрабатываются как буквальный текст. |
| `maxPrice` | Максимальная цена включительно. |
| `sort` | `price`, `-price`, `name`, `-name`; неизвестное значение безопасно возвращает порядок `id ASC`. При равных ключах сортировки добавляется `id ASC`. |
| `limit` | Целое число от 1 до 100; по умолчанию `20`. |
| `offset` | Неотрицательное целое число; по умолчанию `0`. |

Для `GET /api/orders` необязательный `status` принимает только `new`, `processing`, `done` или `cancelled`. Без него возвращаются все заявки; неизвестное, пустое или повторяющееся значение даёт HTTP 400.

Создание заявки из формы React отправляет поля `name`, `email`, `phone`, `quantity`, `date`, `comment` и `product_id`. ID выбранного товара передаётся числом; если товар не выбран, передаётся `null`.

### Централизованная обработка ошибок

`middleware/errorHandler.js` подключён после маршрутов и 404 middleware. Он преобразует известные ошибки PostgreSQL (`22P02`, `23502`, `23503`, `23514`) и ошибки разбора JSON в JSON-ответ 400. Для остальных ошибок возвращается общее сообщение 500; детали и секреты клиенту не выдаются.

## Лабораторная работа №7 — Пользователи и JWT

Цель работы — добавить учётные записи, безопасное хранение паролей,
JWT-аутентификацию и разграничение прав, сохранив каталог и заявки ЛР6.
Запросы идут по цепочке React → Express 5 → PostgreSQL 18 на Ubuntu VMware.
Этот раздел описывает текущее состояние проекта. Числа 16 запросов и 48 проверок выше
относятся к прежней коллекции ЛР6, а её открытые маршруты записи теперь защищены.
PostgreSQL 18 находится в Ubuntu VMware по адресу `<VM_HOST>:5432`;
Express работает на основном компьютере на `localhost:3000`, React — на `localhost:5173`.

### Настройка и миграция

Установите зависимости командой `npm install`. В локальном `.env` задайте
`DATABASE_URL` с действующим адресом VM, `JWT_SECRET` (случайный секрет не короче
32 символов), `JWT_EXPIRES_IN=2h`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` и
`CORS_ORIGIN=http://localhost:5173`. Формат без секретов приведён в
[`.env.example`](./.env.example). Не публикуйте `.env`, дампы или экспорт
окружения Postman.

Для уже существующей базы ЛР6 сначала создайте резервную копию на VM:

```bash
pg_dump -W -h <VM_HOST> -p 5432 -U <DB_USER> \
  -d agromarket -Fc -f "$HOME/agromarket-before-lab7.dump"
test -s "$HOME/agromarket-before-lab7.dump"
pg_restore -l "$HOME/agromarket-before-lab7.dump" >/dev/null
```

Затем один раз примените [`db/migrate-lab7-users.sql`](./db/migrate-lab7-users.sql)
из каталога, куда файл был скопирован на VM:

```bash
psql -W -X -v ON_ERROR_STOP=1 -h <VM_HOST> -p 5432 \
  -U <DB_USER> -d agromarket -f migrate-lab7-users.sql
```

Миграция выполняется в транзакции, создаёт `users` и добавляет необязательный
`orders.user_id` с `ON DELETE SET NULL`. Она не удаляет товары или заявки.
Таблица `users` содержит `id` (первичный ключ), обязательные `name`, уникальный
`email`, `password_hash`, роль `role` с допустимыми значениями `user` и `admin`
(по умолчанию `user`) и `created_at`. Пароль в открытом виде в БД не записывается:
при регистрации и смене пароля используется bcrypt с cost 10.
Повторный запуск завершится ошибкой существующей таблицы без потери данных.
Для новой пустой базы используется `npm run db:init`; для базы после ЛР6 эту
команду запускать нельзя. После миграции создайте администратора командой
`npm run db:admin`. Повторный запуск не создаёт дубль и не меняет пароль.

### Регистрация, вход и доступ к API

`POST /api/auth/register` проверяет обязательные имя, email и пароль длиной от
8 символов, нормализует email и всегда создаёт роль `user`. Повторный email
даёт 409. `POST /api/auth/login` сверяет пароль через `bcrypt.compare` и
возвращает профиль без `password_hash` вместе с JWT.

JWT подписывается `JWT_SECRET`, содержит `sub` и `role`, действует 2 часа.
Токен передаётся в заголовке `Authorization: Bearer <token>`.
`requireAuth` проверяет подпись и срок действия и помещает ID и роль в
`req.user`; `requireRole('admin')` ограничивает административные маршруты.
Отсутствующий или неверный токен даёт 401, недостаточная роль — 403.
`GET /api/auth/me` выбирает из PostgreSQL только `id`, `name`, `email`, `role`
и `created_at`; удалённый пользователь получает 401.

| Метод | Путь | Доступ |
| --- | --- | --- |
| `POST` | `/api/auth/register`, `/api/auth/login` | Публичный |
| `GET` | `/api/auth/me` | Авторизованный пользователь |
| `PATCH` | `/api/auth/password` | Авторизованный пользователь |
| `GET` | `/api/products`, `/api/products/:id` | Публичный |
| `POST`, `PUT`, `DELETE` | `/api/products`, `/api/products/:id` | Только admin |
| `POST` | `/api/orders` | Публичный; с JWT заявка связывается с пользователем |
| `GET` | `/api/orders/my` | Авторизованный пользователь, только свои заявки |
| `GET` | `/api/orders` | Только admin |
| `PATCH` | `/api/orders/:id` | Только admin |

Пароли хранятся как bcrypt-хэши с cost 10. `password_hash` не возвращается из
маршрутов авторизации. Вход ограничен пятью неудачными попытками с одного IP за
15 минут; следующая попытка получает 429. Helmet добавляет защитные заголовки,
CORS разрешает origin React, preflight `OPTIONS` и заголовок `Authorization`.
Размер JSON ограничен 16 КБ, превышение возвращает 413. Журнал не пишет тела,
заголовки и query-параметры запросов.

### Четыре бонуса

1. **Мои заявки:** `optionalAuth` разрешает гостевую заявку и связывает заявку
   авторизованного пользователя через `user_id`; `/api/orders/my` выбирает
   записи только по ID из JWT.
2. **Удаление товара:** администратор видит кнопку подтверждаемого удаления;
   каталог обновляется без перезагрузки страницы.
3. **Смена пароля:** `PATCH /api/auth/password` проверяет старый пароль, требует
   новый длиной не менее 8 символов и записывает только bcrypt-хэш.
4. **Панель заявок:** администратор видит список и меняет статус через
   `PATCH /api/orders/:id`.

### Postman Runner

В [`postman/agromarket.postman_collection.json`](./postman/agromarket.postman_collection.json)
сохранены прежние проверки ЛР6 и добавлены сценарии ЛР7. Выберите окружение
Postman и задайте в нём `userEmail`, `userPassword`, `adminEmail`,
`adminPassword`. Для регистрации на **изолированной тестовой БД** дополнительно
нужны `registerEmail` и `registerPassword`. Значения паролей и JWT не входят в

### Ответы по теме методички и использование ИИ

- bcrypt хранит односторонний хэш с солью, поэтому сервер сравнивает пароль
  через `bcrypt.compare`, не извлекая исходный пароль из БД.
- Подписанный JWT позволяет проверить подлинность и срок действия. `sub`
  указывает ID пользователя, `role` — его права. Подпись не шифрует payload,
  поэтому пароль и секрет в токен не помещаются.
- 401 означает отсутствие действительной авторизации; 403 — действительный
  токен с недостаточной ролью. Проверки выполняются middleware до SQL-запроса.
- `localStorage` сохраняет сеанс после F5, а `/api/auth/me` подтверждает его
  актуальность. При 401 frontend удаляет токен. Для более строгой защиты от
  XSS в производственной системе потребовалась бы отдельная модель хранения
  с HttpOnly cookie и CSRF-защитой.
- ИИ использовался для реализации и проверки SQL, маршрутов, интерфейса и
  тестов. Результаты проверок подтверждались локальными командами; новые
  операции записи на рабочей БД для тестирования не выполнялись.

Файл методички ЛР7 в репозиториях не обнаружен; выше приведены ответы на
вопросы по перечисленным требованиям, без утверждения о дословном составе методички.

## CI/CD

1. Изменения проходят PR → CI и ревью → merge в main. Backend job `test`
   использует отдельную `agromarket_test` в PostgreSQL 16.
2. GitHub Actions запускает `deploy` только после успешного `test` и только
   при push в main. Поэтому в Pull Request деплой пропускается.
   Группа `concurrency: production` исключает одновременное выполнение деплоев.
3. Render Deploy Hook получает `ref=github.sha` и разворачивает проверенный
   коммит. Smoke ждёт его версию в health, затем проверяет каталог, POST без JWT
   → 401, GET с CORS, отсутствующий товар → 404 и категории.
   Каждая проверка выводит отдельный результат; ошибки дают ненулевой код завершения.
   POST отправляет `{}`: даже при потере авторизации валидация отклонит тело.
4. Frontend автоматически собирается Vercel из main. React CI job `build`
   выполняет `npm ci`, lint и build с адресом `https://example.invalid/api`.
   Preview Vercel не работает с production API, если его домен не разрешён в CORS.
5. При аварии — оперативный Rollback на Render, затем `git revert` через PR,
   чтобы отменить проблемные изменения в истории и согласовать main с production.
   Фактический результат упражнения с откатом пока не подтверждён.

## Лабораторная работа №11 — защита backend API

## Архитектура и технологии

Backend — REST API на Node.js 22+, Express 5 и PostgreSQL (`pg`). Маршруты
разделены по товарам, категориям, заказам и авторизации. Для проверки входных
данных используется Zod 4, для паролей — bcrypt, для сессии — JWT. Защитные
middleware подключаются в `app.js`, запуск и проверка обязательной конфигурации
выполняются через `server.js`.

## Защита HTTP API

- Helmet устанавливает заголовки безопасности и Content Security Policy.
- CORS сравнивает Origin с точным allowlist. В коде разрешены
  `https://agromarket-noname523.vercel.app` и `http://localhost:5173`; дополнительные
  точные Origin можно задать через `CORS_ORIGIN` как список через запятую.
  Шаблоны вроде `*.vercel.app` не разрешаются. Запросы без Origin продолжают
  работать, а для постороннего Origin `Access-Control-Allow-Origin` не выдаётся.
- JSON body ограничен 16 KB; превышение возвращает HTTP 413.
- `trust proxy` установлен в `1`, чтобы Express правильно определял клиентский IP
  за одним доверенным reverse proxy.
- Login и register ограничены десятью запросами за 15 минут на IP. Успешные login
  не расходуют IP-лимит. Ответы включают стандартные `RateLimit` headers и
  `Retry-After`. IP-счётчик использует стандартное хранилище express-rate-limit
  в памяти отдельного процесса; межпроцессный лимит по email обеспечивает
  PostgreSQL-механизм ниже.

## Zod, общие схемы и mass assignment

Единственный backend-источник схем находится в `shared/schemas/index.js`.
`middleware/schemas.js` переэкспортирует `registerSchema`, `loginSchema`,
`productSchema`, `productUpdateSchema`, `idParam` и `orderStatusSchema`; серверная
проверка остаётся обязательной независимо от клиентской.

Схемы нормализуют email, ограничивают длины строк, проверяют UTF-8 размер пароля
регистрации (не более 72 байт) и положительную целую цену в диапазоне PostgreSQL
INTEGER. PATCH без допустимых полей отклоняется. `idParam` используется на
маршрутах с `/:id`. Неизвестные поля Zod отбрасывает, а роль при регистрации
задаётся сервером как `user`; клиентское `role: admin` не меняет полномочия.
Ошибки валидации возвращаются как JSON с `error` и `details` (`field` и `message`).

Frontend получает тот же файл из backend Git-репозитория по закреплённому commit
SHA `b01cd2adb29e5394e73671dbc2671580a4ea5466`. Скрипт frontend сверяет SHA-256
`4A97D7D9345B7CFB2FFDA3B7E557D879EB5230C4575D27E2ED68857C0924176F` до записи
игнорируемого `src/generated/schemas.js`; fallback на `main`/`master` не используется.

## JWT и защита входа по email

API использует Bearer JWT с алгоритмом HS256 и сроком действия `2h`. Секрет JWT
не используется для учёта попыток входа.

`services/loginAttemptStore.js` хранит только HMAC-SHA-256 идентификатор
нормализованного email, а не исходный адрес. PostgreSQL резервирует попытки до
bcrypt и атомарно учитывает их между IP-адресами и экземплярами приложения.
После десяти неудачных попыток в 15-минутном окне email блокируется на 60 секунд;
повторные запросы не продлевают блокировку. Успешная авторизация сбрасывает
счётчик. Для неизвестного email выполняется dummy bcrypt-проверка, а ответы на
неизвестный адрес и неверный пароль не раскрывают наличие аккаунта. При ошибке
PostgreSQL login завершается безопасным HTTP 503 без выдачи JWT.

Истечение блокировки и окна учитывается при следующем обращении к email.
Операция `cleanupExpired()` ограничена по объёму, но периодический вызов
очистки в приложении пока не настроен; старые неиспользуемые строки могут
оставаться в таблице до очистки.

## Переменные окружения

Не храните реальные значения в Git и не копируйте production-переменные в
тестовую конфигурацию.

| Переменная | Назначение и требование |
|---|---|
| `DATABASE_URL` | Строка подключения к PostgreSQL. Для тестовых интеграционных запусков используется отдельный `.env.test`. |
| `JWT_SECRET` | Отдельный секрет подписи JWT длиной не менее 32 символов; шаблон `replace-with-...` приложение отклоняет. |
| `JWT_EXPIRES_IN` | Должен быть равен `2h`. |
| `LOGIN_ATTEMPT_SECRET` | Обязательный отдельный HMAC-ключ, минимум 32 UTF-8 байта. Нельзя подменять его `JWT_SECRET`. |
| `CORS_ORIGIN` | В production обязателен; дополнительные разрешённые Origin задаются точными значениями через запятую. |
| `NODE_ENV` | `production` для сервиса; `test` для тестового harness и `db:init`. |
| `PORT` | Необязательный порт HTTP-сервера, по умолчанию `3000`. |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Учетные данные администратора для тестовой инициализации; не публикуйте их. |

Создайте `LOGIN_ATTEMPT_SECRET` криптографически стойким генератором (например,
`openssl rand -hex 32`) и внесите результат только в локальный секрет-хранилище
или настройки сервиса. В текущем `.env.example` и `render.yaml` эта переменная
ещё не объявлена. До запуска backend её необходимо задать в Render и локальном
окружении; без неё приложение безопасно откажется стартовать.

### Проверки без `db:init`

Эти команды не запускают миграции и не подключаются к PostgreSQL:

```bash
npm run test:node
node --test tests/db-test-init-guard.test.js
node --test tests/login-attempt-store.test.js
node --test shared/schemas/tests/schemas.test.js
```

Для PowerShell изолированные Vitest suites можно запустить так:

```powershell
$previousNodeEnv = $env:NODE_ENV
try {
  $env:NODE_ENV = 'test'
  npm run test:vitest -- --config vitest.auth.config.js
  if ($LASTEXITCODE -ne 0) { throw 'Auth suite failed' }
  npm run test:vitest -- --config vitest.security.config.js
  if ($LASTEXITCODE -ne 0) { throw 'Security suite failed' }
} finally {
  if ($null -eq $previousNodeEnv) {
    Remove-Item Env:NODE_ENV -ErrorAction SilentlyContinue
  } else {
    $env:NODE_ENV = $previousNodeEnv
  }
}
```

PostgreSQL integration suites требуют включённую VMware и `.env.test` с точной
целью. Они сами устанавливают `NODE_ENV=test`, повторяют проверку на соединении,
не запускают `db:init` и не выполняют миграции:

```bash
node --test tests/login-attempt-store.integration.test.js
node --test tests/login-route-postgres.integration.test.js
```

При несовпадении фактических базы, адреса, порта или режима теста integration
suite останавливается. Не обходите этот guard и не запускайте suites при
недоступной или неизвестной цели.

> **CI настроен под отдельный режим guard.** `.github/workflows/ci.yml` задаёт
> собственный PostgreSQL service на `localhost`, `CI=true` и фиксированный
> `DB_TEST_PORT=5432`. Guard принимает только эту loopback-цель и локальный
> адрес контейнерного service. После изменения конфигурации GitHub Actions ещё
> не запускался, поэтому успешный результат CI не заявляется.

Проверка зависимостей не устанавливает и не обновляет пакеты:

```bash
npm audit
npm audit --omit=dev
```

## Ответы на вопросы ЛР11

1. **Какие угрозы снижаются?** Перебор паролей по IP и email, попытки mass
   assignment, некорректные и чрезмерно большие JSON-запросы, произвольные
   браузерные Origin и ошибки валидации, которые иначе дошли бы до SQL. React
   отдельно защищает отображение пользовательского текста от HTML-инъекций.
2. **Как работает защита?** Helmet задаёт защитные заголовки; CORS пропускает
   только точные разрешённые Origin; express-rate-limit считает IP-запросы;
   PostgreSQL атомарно резервирует login-попытки по HMAC email; Zod проверяет
   данные до бизнес-логики и SQL.
3. **Как проверить безопасность?** Использовать изолированные тестовые команды
   выше, проверить ответы 400/413/429, `RateLimit` и `Retry-After`, а также
   запускать PostgreSQL integration tests только после подтверждения их target
   guard. Не использовать production credentials для тестов.
4. **Как выполнить rollback?** Откатить приложение на предыдущий проверенный
   deployment через платформу развёртывания. Добавленные таблицы login-attempt
   не требуют удаления для отката старого приложения. Не удаляйте таблицы и не
   выполняйте обратный DDL в production без согласованного плана и резервной
   копии; `db:init` предназначен только для заменяемой тестовой БД и пересоздаёт
   её схему целиком.

## Лабораторная работа №12 — Тестирование и качество

## Роли и границы доступа

В API существуют роли `user`, `admin` и `farmer`. Публичная регистрация (`POST /api/auth/register`) всегда назначает новой учётной записи роль `user`; переданное клиентом поле `role` не предоставляет дополнительные права.

Роль `farmer` разрешает создавать товары через `POST /api/products`. Изменение и удаление товаров (`PUT`, `PATCH`, `DELETE /api/products/:id`) доступны только `admin`. Только `admin` может просматривать административный список заказов и менять статус заказа. Обычные пользователи и фермеры не получают административных полномочий.

## Схема и миграции роли

В `db/schema.sql` ограничение `users.role` для новых схем допускает значения `user`, `admin` и `farmer`. Для существующей production-схемы подготовлен отдельный скрипт `npm run db:migrate:production-farmer` (`db/migrate-production-farmer-role.js`). Он предназначен только для изменения допустимых значений CHECK constraint роли; существующие строки пользователей и другие таблицы не меняются.

Production-миграция требует явного production-режима и подтверждения, проверяет ожидаемые hostname и имя Neon database, TLS и возможности целевого подключения. Она отклоняет локальную и тестовую цель, проверяет фактическую базу до транзакционного изменения и допускает только ожидаемое изменение ограничения роли. Не запускайте её для локальной разработки или тестов; перед отдельным запуском сверяйте целевой Neon endpoint и схему. Сам факт наличия скрипта не означает, что миграция была запущена или что production API проверялся.

Для изолированной тестовой БД предусмотрена отдельная миграция `npm run db:migrate:test-farmer` (`db/migrate-test-farmer-role.js`). Она работает только в тестовом режиме и проверяет имя `agromarket_test`, ожидаемый локальный host и port, включая фактические параметры PostgreSQL до изменения схемы. Скрипт не запускает инициализацию БД и не изменяет строки пользователей.

`npm run db:seed:test-farmer` запускает test-only seed (`db/seed-test-farmer.js`). Он ограничен проверенной `agromarket_test`, использует учётные данные из локального окружения и создаёт тестового farmer или проверяет уже существующий аккаунт, не изменяя его. Если email занят аккаунтом с другой ролью или пароль не совпадает, seed завершается ошибкой. Не переносите эти учётные данные в README, код или Git.
